The brief

Implement and present the LLM-powered planning agent designed earlier in the module. The system must take a goal, plan a sequence of actions, retrieve and process data, and produce a meaningful output in the chosen domain.

The submission is a deck of up to ten slides with an audio transcript, a fully tested codebase with its dependencies, evidence of execution, evidence of testing with any remediation, and a README explaining how to run it. It carries 40% of the module mark.

Assessed on

  • Code quality — the appropriateness of the approach (10%).
  • Meeting the design requirements (25%).
  • Application of concepts and features (30%).
  • Critical commentary within the code explaining design and implementation decisions (25%).
  • Acknowledgement of all sources in the README and code commentary (10%).

What was built

An agent that turns a broad research goal into a reviewed evidence package. It plans searchable sub-questions, retrieves live scholarly records from Crossref and OpenAlex, ranks them, writes one claim per usable abstract that quotes its source, checks every quotation against that abstract, and exports a report only after a person approves it. It implements the six-role design from the Group E report in Unit 6.

The six roles run as functional roles inside one Python and LangGraph process, not as six separately deployed services — a distinction the presentation states explicitly. The design follows Prometheus role decomposition (Padgham and Winikoff, 2003), Plan-and-Execute, and a bounded reasoning-and-acting loop (Yao et al., 2023) rather than unrestricted tool use.

Safeguards in the code

  • Model output must match a Pydantic schema with unexpected fields rejected; one repair attempt is allowed, then the run fails safely.
  • The goal and the retrieved records reach the model as untrusted data, never as instructions. API URLs are fixed in the code, never taken from model output.
  • HTTP error messages omit request URLs, which can carry API keys.
  • Approval accepts only a Boolean, so a string such as "false" cannot approve an export.
  • CSV cells beginning =, +, - or @ are escaped against spreadsheet formula injection.
  • Exports are written atomically, with a SHA-256 manifest.json written last so an incomplete export is detectable.

The workflow

Each role hands to the next until the validator reports. The orchestrator then either sends the run back — one retrieval retry, one processing retry, then one re-plan — or forwards it to the approval gate. Nothing is written to disk before that gate.

The presentation

Ten slides covering the plan, the workflow, three slides of live-run results, the evaluation and the design choices, with the narration script in the transcript. The worked example asks which exercise protocol best reduces knee joint pain.

The deck is careful about what the run does and does not show. The two pre-and-post results on slide 5 were measured on different populations and scales, so they are reported rather than ranked. Slide 6 takes the START trial (Messier et al., 2021) as the strongest comparative source retrieved: at the 18-month WOMAC pain follow-up it found no statistically significant advantage for high-intensity strength training — Δ 0.2 [−0.6, 1.1], p = .61 against attention control, and Δ 0.7 [−0.1, 1.6], p = .08 against low intensity. Both intervals include zero.

Testing

55 offline automated tests passed, with 96.09% statement coverage of the core source. They run with mock model and API clients, so routing, structured data, source matching, approval, export, error handling and notebook wiring are all tested without a live model or academic API. The model gateway and the agent both accept injected clients, which is what makes that possible.

Remediation

  • Two claims quoted text that did not appear verbatim in their abstracts, and the processing retry repeated the error. The supervisor escalated to a re-plan with revised queries, and the new evidence passed every quotation check before approval.
  • The model returned output that failed the schema twice in a row. The bounded repair attempt and processing retry handled it; the run recovered without intervention.

Limitations

  • 55 offline tests and three live runs show that the workflow executes and recovers; they cannot estimate reliability across topics.
  • Exact-quotation checks confirm attribution, not that every summary inference is correct.
  • The relevance score measures term overlap with the goal, not study quality.
  • Evidence comes from metadata and abstracts, not full texts.
  • The model is hosted, so runs depend on provider availability and credits.
  • The approval gate prevents unreviewed exports, but its value depends on the reviewer's attention.
  • The design report's 90% error-free target is a future evaluation criterion, not a result claimed here. The planned 24-goal evaluation against a direct-search baseline has not yet been run.
